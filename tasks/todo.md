- [x] Deploy strategy switched to a `releases/<id>` + atomic `current` symlink pattern (2026-09-03), matching the user's own established convention from other projects. First `release/1.0.0` deploy attempt under the old in-place strategy failed (`Permission denied` on VPS-side `releases`/`shared` dirs the user had already created ahead of this change) — no live outage, nothing was serving yet. Fixed via `hotfix/releases-current-deploy-strategy`: `deploy.yml` rewritten (pinned `VPS_KNOWN_HOSTS` instead of dynamic `ssh-keyscan`, timestamped release dirs, `shared/wwwroot/media` symlinked into each release, prune-to-5, smoke test), `DEPLOYMENT.md` and `SPEC.md` updated to match, systemd unit now points at `<deploy-path>/current`.
- [x] Second deploy attempt (after the releases/current fix) got further but failed at "Write production connection string" -- `/var/lib/neonpixel-website` (the SQLite data dir) didn't exist on the VPS yet, and its literal path was hardcoded in `deploy.yml`/`DEPLOYMENT.md`'s systemd template, which the user flagged as the same "don't commit the production filesystem layout" issue as before. Fixed (2026-09-03) via a second hotfix: new `VPS_ENV_FILE` secret holds the connection-string env file's own path (alongside `VPS_DB_PATH` for the db itself); both `deploy.yml` and `DEPLOYMENT.md`'s systemd unit template now reference these only via secret/placeholder, never a literal value.
- [x] Third deploy attempt got all the way to "Restart service" and failed there: `sudo: A terminal is required to authenticate`. Real bug in `deploy.yml` (not a VPS config issue) -- the sudoers NOPASSWD grant in `DEPLOYMENT.md` is for the exact command `systemctl restart <service-name>.service`, but `deploy.yml` ran `sudo systemctl restart $VPS_SERVICE_NAME` without the `.service` suffix; sudoers matches the full argument list literally, so the mismatch fell through to a password prompt. Fixed (2026-09-03) by appending `.service` in `deploy.yml`.
- [x] Fourth deploy attempt reached "Boot failed" -- not a bug, Umbraco's own "is the database available" check deliberately opens the SQLite file read-only (so a routine health check never has the side effect of creating one), so on a genuinely fresh path with no file yet it reports "unavailable" and retries forever rather than ever creating the file itself. Diagnosed live (2026-09-03) by isolating create-vs-open (manually pre-seeding an empty file unblocked it immediately, install wizard completed, admin user created). Documented in `DEPLOYMENT.md` as a one-time pre-seed step per server, not a pipeline fix.
- [x] After the install wizard succeeded, `theme/wwwroot` static assets (CSS/JS/images/fonts/video) all 404'd in production, blocked by browsers as a MIME-type mismatch (`X-Content-Type-Options: nosniff`). Real bug, never actually exercised end-to-end before this deploy: `Program.cs` served them via a runtime `PhysicalFileProvider` computed relative to `ContentRootPath` (`../../theme/wwwroot`), which only ever resolves in local dev, where `theme/` is a sibling of `src/NeonPixel.Web/` in the same repo checkout -- production's published app has no such sibling directory at all. Fixed (2026-09-03) by pulling `theme/wwwroot` into the project's own publish output at build time via the same MSBuild `Content`/`LinkBase` mechanism already used for `theme/Views`, served through ASP.NET Core's default static-file handling. The original runtime `PhysicalFileProvider` is kept as a second, local-dev-only fallback (guarded by `Directory.Exists`) since `dotnet run`'s `ContentRootPath` is the source project folder, not a publish output, so the MSBuild copy alone doesn't help there. Verified both paths directly: a real `dotnet publish` output run standalone, and `dotnet run` locally.
- [x] Deploy after the `theme/wwwroot` fix landed: every step succeeded (including "Restart service"), but "Smoke test" failed with a 502 -- not a regression, the site was confirmed reachable and correctly serving CSS/JS moments later. Root cause: `systemctl restart` (Type=simple) returns as soon as the process is forked, not once Kestrel is actually ready to accept connections; the smoke test had a single immediate check with no retry. Fixed (2026-09-03) with a 12-attempt, 5-second-interval retry loop in `deploy.yml`.

Six real issues found and fixed along the way (all above): releases/current ownership, external SQLite dir missing, sudoers `.service` suffix mismatch, the read-only-availability-check first-boot gotcha, theme/wwwroot never resolving in production, and the smoke test's cold-boot timing race.
